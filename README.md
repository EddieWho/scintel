# SCINTEL

一个可部署到 GitHub Pages 的供应链调查教学游戏。玩家在有限时间与预算下调查 K2 产品过热事件，阅读证据、比较批次数据、检验竞争假设，并提交处置方案。首版界面为中文，全部企业和数据均为虚构。

## 本地运行

建议使用 Node.js 22 或更新版本。

```sh
npm ci
npm run dev
```

打开 http://127.0.0.1:4173 。前端没有运行时依赖，不需要 API Key、数据库或后端。`npm ci` 安装的是浏览器测试工具；只运行开发服务器时也可以直接执行 `npm run dev`。

```sh
npm test                     # 案例规则与存档验证
npm run build                # 输出 dist/
npx playwright install chromium
npm run test:e2e             # 浏览器流程与响应式验证，使用 dist/
npm run preview              # 本地查看构建产物
```

修改源码后请重新构建，再运行浏览器测试。测试服务器运行在 4175 端口，使用 `/scintel/` 路径验证 GitHub Pages 仓库子路径。开发服务器仅监听本机。

## GitHub Pages 部署

1. 将此目录中的项目上传到一个 GitHub 仓库的 `main` 分支。
2. 在仓库 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。
3. 推送 `main`，或在 **Actions → Deploy SCINTEL to GitHub Pages** 手动运行工作流。
4. 等待构建、规则测试和浏览器测试通过，部署任务会输出网站地址。

已有本地 Git 仓库的情况下，可按实际仓库地址设置远程：

```sh
git add .
git commit -m "Build SCINTEL investigation simulation"
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git
git push -u origin main
```

项目使用相对资源路径和 hash 导航，可部署在 `https://ACCOUNT.github.io/REPOSITORY/`，无需改写仓库名，也无需设置 SPA 路由回退。`dist/` 包含部署所需全部文件；任何静态 HTTP 服务都可以托管。不要直接用 `file://` 打开，因为浏览器会限制 ES 模块加载。

工作流位于 [.github/workflows/pages.yml](.github/workflows/pages.yml)，采用 GitHub 官方 [Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。仓库必须有使用 Pages 的权限；项目本身不创建远程仓库或修改账户设置。

## 一局游戏

1. 接受委托，阅读客户投诉和供应商评分。
2. 选择继续监测、暂停 K2 出货或扩大暂停范围。调查过程中可以升级处置。
3. 使用 100 点预算和 12 个模拟小时开展调查。阅读、分析和写作不消耗时间；仅调查行动推进模拟时间。
4. 阅读解锁材料。批次追踪会开启供应商、工厂和批次分析，可记录不同的数据比较。
5. 将已阅读证据与三个竞争假设建立支持或反驳关系，再选择当前判断。
6. 提交召回范围、供应措施、检验安排及至少 20 字的理由。不强制调查全部材料，即使预算耗尽也能提交。
7. 查看解释性评分、模拟后果和案例真相，填写反思，下载报告。

提交前有确认步骤；提交后行动、假设、证据关系及决策依据锁定，反思仍可编辑。重新开始会清除当前浏览器中的本次进度，需要再次确认。

## 保存与报告

- 当前调查自动保存在浏览器 `localStorage`，刷新后可恢复。不跨浏览器、设备或不同网站域名同步。
- 存档会校验版本、案件标识、资源余额、解锁条件、调查顺序和处置时机。损坏或不兼容的存档会安全回到新案例。
- 禁用本地存储时仍可完成当前会话，页面会明确提示无法保存。
- HTML 报告包含决策依据、证据登记表、假设矩阵、分析记录、评分、反思与行动时间线。下载后可在浏览器打印为 PDF。
- JSON 导出包含完整调查状态及评分，方便教师人工汇总；首版不提供在线收集、教师账号或实时班级后台。
- 所有文本在页面和 HTML 报告中转义，自由文字不会作为 HTML 执行。

## 文件结构

```text
index.html                   页面入口
src/app.js                   界面、交互、本地保存与报告导出
src/styles.css               桌面、平板、手机与打印样式
src/case.js                  案例材料、批次数据、行动与关系规则
src/engine.js                状态转换、资源约束、评分、后果、存档校验
scripts/build.mjs            生成静态发布目录
scripts/serve.mjs            本地预览服务器
tests/engine.test.js         规则测试
tests/browser/game.spec.js   完整操作流程与响应式浏览器测试
```

案例内容由 `src/case.js` 维护，当前引擎针对这个案例设计。证据编号、调查 ID 与评分规则有关联；改变它们时必须同步更新引擎和测试，不能仅上传文件就生成新案例。已有存档依赖案例版本；更改核心规则后需提升版本并调整应用存储键。

## 教学范围

这是结构化调查练习。系统评价可观察的证据关系、假设检验和处置选择，不声称理解自由文字的推理质量。自由文字与反思应由教师或小组讨论评价。

评分规则和案例答案随前端一起发布，不能作为防作弊考试平台。模拟后果是固定教学模型，不是真实供应链预测。未实现在线多人、聊天、登录、无代码场景编辑器、AI 服务或真实企业数据接入。

## 评分和后果模型

以下规则供教师和维护者审核，包含案例答案。页面只在提交后揭示评估结果。

| 维度     | 上限 | 主要规则                                                                                                                     |
| -------- | ---- | ---------------------------------------------------------------------------------------------------------------------------- |
| 证据整理 | 40   | 正确关联获得该证据权重，仅阅读获得 25%；错误关系扣分。达到 24 个有效权重点即可满分，不要求收集所有证据。                     |
| 假设论证 | 30   | 最符合案例的假设基础 12 分，其他假设 8 分；正确支持、检验替代解释和记录比较可加分，与所选假设矛盾的证据及错误连接扣分。      |
| 决策质量 | 30   | 实际暂停 K2 出货 10 分；初始即采取保护 5 分，2 小时内 3 分，更晚 1 分；供应措施最高 7 分，产品处置最高 5 分，检验最高 3 分。 |

证据 E01 至 E10 的权重依次为 `2, 1, 5, 6, 4, 6, 4, 8, 3, 1`。每份证据的错误关系扣分为 `min(该证据权重 × 0.55, 错误关系数量 × 2)`。证据总权重先除以 24 再乘以 40，取整并限制在 0–40。

所选假设的正确支持获得对应证据权重的 50%；正确识别与所选假设矛盾的证据会扣该权重的 55%，因为最终仍选择了被该证据反驳的解释。其他错误连接同时影响关系质量。对其他机器/设计解释的有效检验每项加 1.5 分；不同分析记录每项加 1.5 分、最多 4 分。分数始终限制在各维度上限内。自由文字只检查完成度，不对语义自动评分。

定向召回的完整得分需要阅读 E03、E04，暂停涉事供应来源的完整得分需要 E06 或 E08 的来源证据。暂停全部型号和暂停 K2 的保护得分相同，但前者占用更多资源。仅有投诉或陈旧绿色评分，不能直接支持“供应商替换元件”的结论。

后果模型使用一个抽象暴露指数：调查每消耗一小时，在继续出货时增加 8 点，暂停 K2 或全部型号后增加 1 点。指数不是预计受伤人数。较晚采取保护无法消除已经积累的暴露。

```text
成本指数 = 已用调查预算 + round(暴露指数 / 8)
         + 召回项（定向 4 / 全部 K2 11 / 不召回 0）
         + 供应项（暂停切换 6 / 核验 3 / 维持 0）
         + 检验项（增强 4 / 常规 1）
示意成本 = 成本指数 × ¥1,000

额外交付天数 = 2 + ceil(已用调查小时 / 4) + ceil(暴露指数 / 16)
             + 召回项（全部 K2 2 / 不召回 4 / 定向 0）
             + 暂停项（全部型号 2 / K2 1 / 继续出货 0）
             + 供应项（暂停切换 1 / 核验 2 / 维持 0）
             + 检验项（增强 1 / 常规 0）
```

继续出货、不召回、维持涉事采购，或没有追踪依据却定向召回，都会留下高风险。及时暂停 K2、有效召回、暂停涉事来源、增强检验且暴露不超过 8 点时为低风险；其他组合为中风险。过程分数与后果分开展示；较低成本本身不意味着更好的判断。
